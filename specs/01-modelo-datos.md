# 1. Objetivo en una frase

Definir el esquema relacional de la base de datos para el Sistema de Citas Veterinarias (Laboratorio 23), de modo que soporte propietarios, mascotas y citas con integridad referencial y permisos mínimos para el acceso desde la aplicación.

# 2. Alcance

- Crear la tabla `propietarios` con sus campos y restricciones.
- Crear la tabla `mascotas` con sus campos, restricción de llave foránea hacia `propietarios(id)` y clave de integridad.
- Crear la tabla `citas` con sus campos, restricción de llave foránea hacia `mascotas(id)` y clave de integridad.
- Definir permisos `GRANT` para el rol que usará la aplicación (política de acceso mínimo).
- Insertar entre 3 y 5 registros de ejemplo por tabla.
- Decidir la activación/desactivación de Row Level Security (RLS) y justificar la decisión.
- No incluye la implementación del frontend ni la creación de funciones/trigger RPC.

# 3. Modelo de datos

## Tablas

### propietarios
| Columna  | Tipo         | Nulo | Default | Restricciones |
|----------|--------------|------|---------|---------------|
| id       | bigint (PK)  | NO   | `generated always as identity` o `generated by default as identity` (preferir `always`) | PRIMARY KEY |
| nombre   | text         | NO   |         |              |
| telefono | text         | NO   |         |              |
| correo   | text         | NO   |         | UNIQUE       |

### mascotas
| Columna      | Tipo        | Nulo | Default | Restricciones |
|--------------|-------------|------|---------|---------------|
| id           | bigint (PK) | NO   | identity | PRIMARY KEY |
| nombre       | text        | NO   |         |              |
| especie      | text        | NO   |         |              |
| raza         | text        | NO   |         |              |
| propietario_id | bigint    | NO   |         | NOT NULL; FK a propietarios(id) ON DELETE RESTRICT; ON UPDATE CASCADE |

### citas
| Columna   | Tipo        | Nulo | Default | Restricciones |
|-----------|-------------|------|---------|---------------|
| id        | bigint (PK) | NO   | identity | PRIMARY KEY |
| mascota_id | bigint     | NO   |         | NOT NULL; FK a mascotas(id) ON DELETE RESTRICT; ON UPDATE CASCADE |
| fecha     | timestamptz | NO   |         |              |
| motivo    | text        | NO   |         |              |
| estado    | text        | NO   |         |              |

## Relaciones
- `mascotas.propietario_id` → `propietarios.id` (uno-a-muchos: un propietario tiene muchas mascotas)
- `citas.mascota_id` → `mascotas.id` (uno-a-muchos: una mascota tiene muchas citas)

## Permisos GRANT
- Conceder al rol de aplicación (`anon` y/o `authenticated`, según corresponda al uso con el cliente Supabase) únicamente los privilegios mínimos necesarios: `SELECT`, `INSERT`, `UPDATE`, `DELETE` sobre las tres tablas, **solo si** el flujo de la app los requiere.
- No conceder privilegios sobre esquemas del sistema ni sobre otras tablas.
- Justificación: se aplica principio de mínimo privilegio.

## RLS (Row Level Security)
- **Decisión:** *Desactivado* para las tres tablas en esta fase.
- Justificación: la aplicación usará el cliente Supabase con las claves públicas y el acceso se controla mediante permisos `GRANT` a nivel de tabla/rol. Activar RLS sin definir políticas precisas puede bloquear operaciones esperadas y, en este laboratorio (planificación inicial, sin autenticación de usuarios todavía), desactivarlo permite verificar la creación de datos con consultas simples y garantiza que `arquitecto-bd` pueda crear/verificar la estructura sin ambigüedad.

# 6. Decisiones tomadas y descartadas

**Tomadas:**
- Usar `bigint` con `identity` para `id` (compatibilidad con Supabase/Postgres). Se prefiere `generated always as identity` para evitar asignación manual accidental.
- Usar `timestamptz` para `fecha` (soporta zona horaria y comparación correcta).
- `ON DELETE RESTRICT` para evitar borrar propietarios/mascotas con citas; `ON UPDATE CASCADE` para propagar cambios de id.
- RLS desactivado en esta fase (control vía `GRANT` + no hay auth implementada aún).
- Permisos mínimos: solo `SELECT/INSERT/UPDATE/DELETE` a las tres tablas, sin privilegios de esquema.

**Descartadas:**
- Usar `serial` (obsoleto en favor de `identity`).
- Usar `date` para `fecha` (se requiere hora para la cita).
- Activar RLS ahora sin definir políticas (complicaría la verificación con MCP y sin login).
- Crear `mascota_id`/`propietario_id` como `uuid` (no solicitado; se usa `bigint identity` coherente con simplicidad del laboratorio).
